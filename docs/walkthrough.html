1. What this repository is

This is not a library you import. It is an opinionated workflow for impact evaluation, designed so that AI agents (or a disciplined human) produce a causal estimate the same careful way every time. The repo ships the scaffolding and the rulebook; the analysis code is written only after the design is settled.

The core stance. Start with the causal question, the estimand, and the identification logic — everything else follows. Never "run models until something works." No estimation code exists until a DAG and an identification strategy do.

2. The three pillars

📋 configs/project.yaml

The single source of truth. What the intervention is, who was treated, the outcomes, the pre-treatment covariates, and where the raw data lives. Agents read this first and never re-ask what it already answers.

📚 the causal-inference skill

.github/skills/causal-inference/ holds the 10-step methodology plus reference files (design playbook, DAGs, diagnostics, refutation). Every agent loads it before acting; when it conflicts with intuition, the skill wins.

🤖 the agents

.github/agents/ defines Planner, Implementer, Reviewer, and an Orchestrator. Each owns a slice of the workflow and hands off only when guardrails pass.

3. The 10-step canonical workflow

Steps 1–5 are THINKING — no code is written. Steps 6–10 are CODE. The order is enforced, not advisory.

  1. Formulate — treatment, outcome, population, time zero, follow-up window, estimand (ATE/ATT/CATE/LATE), decision context.THINKING
  2. Design — eligibility, treatment strategy, timing, censoring, SUTVA. For observational data, emulate a target trial.THINKING
  3. DAG — an explicit causal graph: confounders, mediators, colliders, unobserved common causes. No DAG, no estimation.THINKING
  4. Identify — pick a route (backdoor / IV / DiD / RDD / ITS / synthetic control / g-methods) and state the assumptions. Stop if "not identified."THINKING
  5. Choose estimator — match it to the identified problem, not to fashion.THINKING
  6. Estimate — write code now. Check the environment; use only causally admissible covariates.CODE
  7. Diagnose — overlap/positivity, covariate balance, functional form, design-specific checks.CODE
  8. Refute — at least one falsification or sensitivity check; negative controls when available.CODE
  9. Interpret — in terms of the estimand, the supported population, and decision-relevant units.CODE
  10. Report — assumptions first, estimate second, with calibrated language.CODE
Hard stops the agents enforce: no DAG → blocks identification · status not "identified" → blocks estimation · structural positivity violation → blocks estimation · failed diagnostic guardrail → blocks reporting. A failed guardrail produces no summary artifact — there is no "emit with a warning" fallback.

4. The agents and how work flows

Planner Steps 1–5

Reads project.yaml, runs structural EDA, emulates a target trial, draws the DAG, writes the identification block, picks an estimator. Writes the plan to docs/plans/<slug>.md and decisions to <slug>-design.yaml. Writes no estimation code.

Implementer Steps 6–10

Executes the approved plan in order: data prep → estimation → diagnostics → refutation → reporting. If a guardrail fails it stops and surfaces the failure instead of emitting results.

Reviewer

Audits design and code, classifies every finding as design-level (back to Planner) or code-level (back to Implementer), and emits a routing block. Iterate until terminal; then export a Word report.

Orchestrator

Optional single entry point. Reads project.yaml, checks what already exists in docs/plans/, and routes to the right agent at each stage.

# the loop
project.yaml  ─►  Planner  ─►  [plan + design.yaml]  ─►  Implementer  ─►  [results + report]
                    ▲                                          │
                    └──────────  Reviewer  ◄───────────────────┘
                       (design-level vs code-level routing, until terminal)

5. Worked example — manager leadership program

The shipped project.yaml describes a real-shaped problem: L&D ran a 3-month leadership program (Jan–Mar) to lift manager effectiveness and cut turnover. Participation was voluntary, and some departments pushed it harder than others.

Treatment

Entered the program (1/0). 570 of 9,000 managers (6.3%).

Outcomes (June, 1–5)

Manager Efficacy Index (primary), Stay Intention, Workload. Prior-year baselines available.

The catch

Voluntary uptake → better, more motivated managers self-select in. A naive comparison is badly biased.

Why the data is synthetic with a known answer. The README references a dummy dataset that was never actually committed (data/** is gitignored). So the example ships a generator that bakes in a true effect — Efficacy +0.30, Stay +0.25, Workload +0.15 — letting us check the workflow against ground truth instead of taking it on faith.

6. Design and the DAG

Estimand: the ATT — the effect on managers who actually chose to attend. That is the decision-relevant quantity for "should we keep offering this," and it is honest about the fact that we never randomized.

Target trial: randomize program access among all managers in post in January; measure the June indices and 12-month retention. The observational data approximates it by adjusting for everything that drives both enrollment and outcomes.

Manager quality / motivation (Q, partially UNOBSERVED) │ ╲ ▼ ▼ performance, Enrollment (T) ─────────► Efficacy_followup (Y) baseline scores ◄──┐ ▲ ▲ │ │ │ │ └────────────┘ dept_promo_intensity │ │ baseline_efficacy ──────────────────(direct path)─────┘

Adjust for baseline survey indices, performance, tenure, team size, span of control, demographics, org/region/job family, dept promotion intensity. Excluded as post-treatment: all follow-up outcomes and retention flags. The threat: latent motivation Q is only partly captured by observed proxies → residual confounding.

7. The identification block

Identification strategy: backdoor adjustment (conditional exchangeability)
Required assumptions:
  1. Conditional exchangeability given the adjustment set      — IDENTIFYING, partly untestable
  2. Positivity for the treated (every treated unit has        — TESTABLE (see diagnostics)
     control support)
  3. Consistency / well-defined treatment version              — IDENTIFYING
  4. SUTVA / no interference between managers                  — IDENTIFYING, plausible
Identification status: identified  (conditional on assumption 1)

Estimator (step 5): AIPW (doubly robust) as primary — robust to misspecification of either the outcome or the propensity model — with ANCOVA and IPW as cross-checks, and the naive difference shown only to expose the bias.

Selection bias is huge

Naive efficacy (+1.03) is 3× the truth. Better managers opt in. Adjustment removes ~75% of that gap.

Confounding flips signs

Naive workload looks negative; once adjusted, it is correctly positive. The raw number was backwards.

Adjustment isn't magic

Estimates land slightly above truth — residual confounding from motivation that the proxies miss.

9. Diagnostics & refutation

Diagnostics

PASS  Balance: max |SMD| after IPW weighting = 0.023 (guardrail < 0.10). Performance rating alone went from SMD 1.10 before to 0.005 after.

PASS  ATT positivity: only 0.35% of treated managers fall outside control support; 0% have PS > 0.98.

≈41% of controls sit at PS < 0.02 — expected for a rare program and harmless for ATT, since those controls carry ≈0 weight. (The generic "<5% extreme PS" rule is the wrong guardrail for a rare-treatment ATT design; the plan uses the treated-support check instead.)

Refutation

PASS  Placebo treatment (labels shuffled): ATT = −0.028 ≈ 0. The pipeline does not manufacture effects from noise.

STABLE  Trim-to-overlap: ATT = 0.416, unchanged from the full sample.

MODERATE  E-value = 2.45 (CI bound 2.27). An unmeasured confounder would need a ~2.4× association with both enrollment and efficacy, beyond the measured covariates, to explain the estimate away. Manager motivation is a plausible candidate at moderate strength — consistent with the small upward residual bias we see.

10. Interpretation — calibrated language

The results are consistent with a positive causal effect of the program on participating managers: roughly +0.3 to +0.4 points on Manager Efficacy and ~+0.3 on Stay Intention (1–5 scale), for the kind of manager who chooses to attend (the ATT). The Workload effect is small and least robust.

The repo's reporting rule ties wording to evidence strength: clean assumptions + clean diagnostics + clean refutation → "estimated causal effect"; one or two concerns → "consistent with a causal effect"; weak design → "association not robust to…". Here we land on the middle tier, because the no-unmeasured-confounding assumption can't be fully verified and the E-value says robustness is moderate, not overwhelming.

Decision takeaway: the evidence supports continuing the program, with two strengthening steps before scaling — corroborate with the behavioral retention outcome, and introduce randomized encouragement (e.g. randomized invitations) so the next evaluation can lean on an instrument instead of the no-unmeasured-confounding assumption.

11. Run it yourself

pip install -e . matplotlib

python scripts/00_generate_dummy_data.py   # writes data/raw/manager_data.csv (570 treated / 9,000)
python scripts/01_prepare_data.py          # propensity score + common-support flag
python scripts/02_estimate.py              # estimates, diagnostics, refutation, report
pytest tests/ -q                           # 3 guard tests (ATT weights, SMD, AIPW recovery)

Artifacts land in results/summary.json, reports/tables/, reports/figures/, and the narrative report at reports/manager-leadership-report.md. The approved plan lives in docs/plans/manager-leadership.md with decisions in the companion -design.yaml.

To use it on your own project

Replace configs/project.yaml with your intervention, drop your immutable source files in data/raw/, then ask the Planner to read the config and prepare a plan. Everything downstream follows the same 10 steps.
